# aitravel

The **AITravel** iOS app's Go API (`OptimusFoundry/AITravel`, `base-server/`)
served at `aitravel.protoapp.xyz/api`. Prototype tier.

The client is a native iOS app, so only `/api/*` carries traffic. The module's
webapp bucket and CloudFront distribution exist because every product is
routed the same way (CloudFront → shared ALB with `X-Product-Id: aitravel`),
but the SPA origin is empty.

## What this stack owns

| Resource | Name |
|---|---|
| Webapp bucket + CloudFront | `protoapp-aitravel-webapp` (module convention) |
| API service | ECS `aitravel-api`, ECR `aitravel-server`, target group `aitravel-api-tg` |
| Migrator | task definition `aitravel-migrator` (no service), ECR `aitravel-migrator` |
| Logs | `/aitravel/api` — stream prefixes `api` and `migrator` |
| Media bucket | `protoapp-aitravel-media` (**private**) + IAM user of the same name |
| SSM | `/aitravel/*`, plus the deploy manifest `/aitravel/manifest` |
| ALB rule priority | **310** (sjocamp 100, meerkat 200, orca 300) |
| Terraform state | `s3://aitravel-terraform-state` |

CloudFront's `ALB-API` origin read timeout is **60 s** here
(`api_origin_read_timeout`), not the 30 s default: Gemini tool-loop day
generation can take longer than 30 s before the first byte.

## Deploys

The app repo's `.github/workflows/aitravel-server.yml` deploys on push to
`main`, assuming `github-actions-admin-aws` through the platform's GitHub OIDC
trust (the AITravel subject lives in `platform/variables.tf`). It reads every
identifier from `/aitravel/manifest`:

| Manifest key | Used for |
|---|---|
| `aws.ecrRepository`, `aws.migratorEcrRepository` | image pushes (repository **names**) |
| `aws.migratorTaskDefinition` | `aws ecs run-task` before the deploy; container `migrator` must exit 0 |
| `aws.ecsCluster`, `aws.ecsService` | force a new deployment of `aitravel-api` |
| `aws.logGroup` | printing the migrator log when the migration fails |

Both ECS task definitions point at `:latest`. Until the first CI run pushes
images, `aitravel-api` keeps failing to pull — expected.

## Runtime configuration

Everything is plain task-definition `environment` (the platform `ecsTaskRole`
has no `ssm:GetParameters`). Values Terraform sets literally rather than from
SSM:

| Var | Value | Why |
|---|---|---|
| `GO_ENV` | `production` | turns on production-only checks: fake billing refused, test-login route not registered |
| `GIN_MODE` | `release` | |
| `PAYMENTS_PROVIDER` | `disabled` | no billing on this server; Apple endpoints answer 503 `BILLING_DISABLED` |
| `EVENTS_TOPIC` / `EVENTS_RESEND_TOPIC` / `EVENTS_CONSUMER_GROUP` | `aitravel.webhook-events` / `aitravel.resend.email.events.v1` / `aitravel.webhook-consumers` | slug-prefixed on the shared broker |
| `DB_MAX_OPEN_CONNS` / `DB_WORKER_MAX_OPEN_CONNS` | `10` / `5` | the shared RDS is a `db.t3.micro` (~112 connections) |

## Secrets

Account-wide values come from `/platform/*` through `data.tf`: resend, gemini,
stripe secret key, RDS host/port. **Not** the RDS master credentials —
aitravel connects as its own role.

Per-product values come from the gitignored `secrets.auto.tfvars`, rendered
from env-registry:

```bash
make secrets PRODUCT=aitravel
make check-secrets PRODUCT=aitravel
```

`cloudflare_email` goes in the gitignored `terraform.tfvars`
(see `terraform.tfvars.example`).

| Value | State |
|---|---|
| `auth_jwt_secret` | **Real, generated fresh** (`openssl rand -base64 48`). Never copy a sibling's — its sessions would be valid here |
| `maps_places_api_key`, `maps_routes_api_key` | **Real** — place enrichment needs them |
| `email_sender_address` | `no-reply@protoapp.xyz`, already Resend-verified |
| `email_resend_webhook_secret` | **Placeholder** — no aitravel Resend webhook endpoint is registered |
| `payments_stripe_webhook_secret` | **Placeholder**, copied from meerkat as orca did — iOS never uses Stripe |
| `auth_google_oauth_client_id` / `_secret` | **Placeholder**, any non-empty value — boot requires them, iOS signs in with email/password, and nothing calls Google at boot |

Media-bucket credentials and the DB password are generated by this stack and
feed the task definitions directly — no tfvars round-trip.

## Database

aitravel connects as a dedicated role, `aitravel_app`, which owns the
`aitravel` database — not as the RDS master user orca, meerkat and sjocamp use.
Terraform generates the password (`random_password.db_app` →
`/aitravel/db/password`); the role and database are created by hand once,
**after** the first apply and before the first deploy.

Port-forward as in `RUNBOOK.md` (or `products/orca/README.md` § 2), then
connect as the RDS master user:

```bash
AITRAVEL_DB_PASS=$(aws ssm get-parameter --name /aitravel/db/password --with-decryption --query Parameter.Value --output text)

PGPASSWORD="$RDS_MASTER_PASS" psql -h localhost -p 15432 -U "$RDS_MASTER_USER" -d postgres \
  -v pw="$AITRAVEL_DB_PASS" <<'SQL'
CREATE ROLE aitravel_app LOGIN PASSWORD :'pw';
GRANT aitravel_app TO CURRENT_USER;
CREATE DATABASE aitravel OWNER aitravel_app;
REVOKE aitravel_app FROM CURRENT_USER;  -- optional
SQL
```

The master user is `rds_superuser`, not a true superuser, so it must be a
member of `aitravel_app` before it can create a database owned by it. Do not
use a `GRANT ALL PRIVILEGES ON DATABASE` pattern — ownership already gives the
role everything, including `CREATE` on the PG15+ `public` schema. No extension
step either: `uuid-ossp` is trusted on RDS, so Flyway's first migration creates
it as the owner.

Schema migrations run from CI through the migrator task, never by hand.

### Rotating the DB password

The password lives in two places — Postgres and Terraform state — and they
must end up equal. Order matters:

- **Postgres first is the safe direction.** Run
  `ALTER ROLE aitravel_app PASSWORD '<new>';` on RDS, then make Terraform hold
  that same value and apply. Existing pooled connections stay authenticated;
  new ones use the new value once the task definition rolls.
- **Applying first breaks the API.** A new `random_password` value reaches the
  task definition before Postgres knows it, and every new connection is
  rejected until `ALTER ROLE` catches up.

Note that `random_password` cannot be given a value: `terraform apply
-replace=random_password.db_app` always generates a *new* one, unknown until
apply. Rotating that way therefore means accepting a short outage — apply,
read the new value from `/aitravel/db/password`, `ALTER ROLE` to it
immediately, then redeploy. For a zero-outage rotation, first add an explicit
password input in front of `random_password.db_app`.

## Capacity

The ECS cluster is a single `t4g.large` (2048 CPU units, ~7.6 GiB). CPU is the
binding constraint. Terraform-declared reservations before this stack: kafka
512, orca api 128, orca render 512, meerkat api 64, meerkat capture-worker 512,
sjocamp 64 = **1792**, leaving 256 free.

| State | aitravel CPU | Free CPU |
|---|---|---|
| Steady state (api) | 64 | **192** |
| Migrator running (stops before deploy) | 128 | 128 |
| Rolling deploy (100/200) | 128 | 128 |

Memory reservations total about 4.3 GiB of ~7.6 GiB with aitravel's 256 MiB.
CPU units are scheduler shares, not caps, so the server still bursts on an
idle host.

Remaining collision risk: an orca-api roll (+128) and an aitravel roll (+64) at
the same moment need exactly the 192 free units — zero margin. Add a concurrent
migrator run or a meerkat-api roll and one deploy waits for capacity until the
other finishes; it does not deadlock, because each roll frees its old task.

## Bootstrap checklist

1. Platform apply with the AITravel OIDC subject (`platform/variables.tf`).
2. `make secrets PRODUCT=aitravel`; put `cloudflare_email` in `terraform.tfvars`.
3. `terraform -chdir=products/aitravel init`, then plan to a file, read it,
   apply that file.
4. Create the role and database (§ Database).
5. Merge/run the app repo's deploy workflow — it pushes both images, runs the
   migrator, deploys and verifies.
